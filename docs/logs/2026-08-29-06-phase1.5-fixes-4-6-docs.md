## What changed

- **`docs/TRAINING_EXPOSURE_MODEL.md`** (Fix #4, the spec's "most
  important next step"). Written only after actually inspecting
  `src/blueprint/snapshot/exercises.json` field-by-field (a Python
  one-liner census of every optional field's key-presence and shape —
  not assumed from memory). Key finding driving the whole document:
  Blueprint has no per-target weighting anywhere in its data; where two
  targets need materially different treatment from what looks like one
  exercise, Blueprint's own authors split it into two exercise records
  (`dip-chest-biased` / `dip-triceps-biased`) instead of inventing a
  percentage split. The doc walks through direct exposure (A, directly
  supported — `physique_targets`/`functional_goals` membership), indirect
  exposure (B, undecided — `secondary_targets` is free text, not
  id-resolvable), set contribution (C, a candidate default proposed, not
  adopted), uncompleted sets (D, recommended default, still flagged),
  intensity/RIR-RPE (E, blocked on logger UI work that doesn't exist yet),
  goal weighting (F, design direction only), and aggregation (G, a query
  shape once A-F are decided, not a data problem). No exposure-computation
  code was written — `TrainingExposure`'s contract shape in
  `src/contracts/types.ts` is unchanged from Phase 1.

  Side fix discovered during the field census: `src/blueprint/types.ts`
  typed `physique_targets`/`functional_goals` as always-present-but-
  nullable, but the real data omits the JSON key entirely on ~8%/~94% of
  records (not just sets it to `null`). Corrected both to optional keys
  (`physique_targets?: string[] | null`) with a doc comment explaining
  why, and confirmed via `grep` that every existing call site already used
  a `?? []`/`?? null` fallback — no behavioral change, just an accurate
  type.

- **`docs/open-decisions.md`** (Fix #6). Storage item rewritten to the
  spec's exact template (`Production persistence: OPEN` /
  `Current development storage: SQLite` / `Reason` /
  `Production requirement`), with an explicit "don't replace SQLite over
  this" note. Cross-referenced items #2 (Blueprint reproducibility, now
  partially addressed by `Program.blueprint_commit`), #3 and #4 (now point
  at `docs/MIGRATION_PLAN.md` and `docs/CALORIE_TRACKER_INTEGRATION.md`),
  and #6 (now points at the new design doc instead of restating it).

- **`docs/architecture.md`** gained a new §4 "Responsibility boundary":
  the three-app ASCII diagram from the spec, plus explicit "must never
  become responsible for" lists per app (Calorie Tracker: exercise
  selection/volume/program generation/progression; workout-logger: food
  logging/nutrition targets/TDEE; workout-blueprint: any user-specific
  state). The "Data contract" section was updated to mention
  `TrainingProfile` and `blueprint_commit`, and §3 to mention the new
  `users`/`training_profiles` tables.

- **`docs/CALORIE_TRACKER_INTEGRATION.md`** — new. Formal one-way contract
  write-up: exact input shape `getCompletedWorkouts(date)` returns,
  explicit statement that Workout Programmer never computes or owns a
  calorie number, and that neither app depends on the other's internal
  schema.

- **`docs/MIGRATION_PLAN.md`** + **`scripts/migrate-workout-log-dry-run.mts`**
  — new. A field-by-field mapping of every `workout_log.csv` column to the
  new schema (or an explicit "no equivalent" flag for `games`/`format`;
  `tdee_final` explicitly never migrated, per the responsibility
  boundary). The dry-run tool is real and tested
  (`tests/migrationDryRun.test.ts`, 6 tests, run against a synthetic
  sample CSV): it parses a CSV, proposes Blueprint exercise-id candidates
  for free-text workout names via plain token-overlap similarity (never
  an auto-decided mapping), flags unparseable weight/reps values, and
  never writes to workout-logger's database. It has **not** been run
  against the real `food_and_workout_tracker` CSV — this session has no
  access to that repository or file; doing so, and reviewing the output,
  is the next step before any import decision.

- `README.md` updated throughout to reference the new docs and the
  Training Profile / goal-id-distinction / Blueprint-version-tracking
  additions from the previous commit.
