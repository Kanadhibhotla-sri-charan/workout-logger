# Change log: Phase 1.5 fixes #1, #2, #3, #5

- **Date:** 2026-08-29
- **Commit:** `eba5bbf`
- **Source:** `workout_programmer_phase1_5_shortcomings.md`, a remediation
  spec Charan provided reviewing the Phase 1 implementation. The Phase 1
  architecture was approved as-is; this is targeted fixes, not a rewrite.

## What changed

- **Fix #1 (completed-workout export contract).**
  `src/services/calorieTrackerExport.ts`: `getCompletedWorkouts(db, date)`
  now filters to `status === 'completed'` only. Added a separate
  `getWorkoutSessions(db, date)` for the all-statuses history view (now
  used by `/api/export/workout-sessions`), so the two meanings are never
  overloaded on one function, per the spec's explicit instruction.
  `tests/calorieTrackerExport.test.ts` gained a parametrized case per
  status (planned/in_progress/completed/skipped) plus a mixed-date case
  and a `getWorkoutSessions` case.

- **Fix #2 (user training profile).** New `users` and `training_profiles`
  + `training_profile_activities` tables (`src/db/schema.sql`); new
  `UsersRepo` (single-user `getOrCreateDefault()`) and
  `TrainingProfileRepo` (`src/repositories/`); new `TrainingProfile`,
  `RecurringActivity`, `Weekday`, `ActivityType` contract types
  (`src/contracts/types.ts`); new `/api/training-profile` (GET/PUT) route;
  new `public/profile.html` UI page, linked from every page's nav.
  `training_days`, `preferred_split`, session-duration bounds,
  `available_equipment`, and `other_activity_schedule` are all read/written
  as data — nothing about a specific schedule is hard-coded.
  `available_equipment` entries are validated against
  `BlueprintAdapter.getEquipmentList()` at write time
  (`UnknownBlueprintEquipmentError` on an unknown id). 6 new tests in
  `tests/trainingProfile.test.ts`.

- **Fix #3 (local Goal vs Blueprint goal distinction).**
  `src/repositories/goalsRepo.ts`: `GoalsRepo.create()` now validates
  `blueprint_ref` against `BlueprintAdapter` itself (previously only the
  Express route checked this) and throws
  `UnknownBlueprintGoalReferenceError`, persisting nothing, on an invalid
  or wrong-goal-type reference. Added `GoalsRepo.resolveBlueprint(goal.id)`
  as the single one-way resolution path (`goal.id` -> stored row ->
  `blueprint_ref` -> `BlueprintAdapter`), plus `GET /api/goals/:id/blueprint`.
  Expanded the `Goal` type's doc comment in `src/contracts/types.ts` to
  spell out why `id` and `blueprint_ref` must never be conflated. New
  `tests/goals.test.ts` (5 tests) plus the spec's own fixture,
  `tests/fixtures/armSideThickness.test.ts` (5 tests): proves
  `arm-side-thickness` resolves to primary target
  `brachialis-arm-thickness` / supporting `triceps` against the real
  Blueprint snapshot, that a stored Goal survives reload, and that a
  logged workout's exercise can be traced back to the same targets the
  goal cares about.

- **Fix #5 (Blueprint version as first-class).** `Program` gained
  `blueprint_commit` (`src/contracts/types.ts`, `src/db/schema.sql`,
  `programs` table now `NOT NULL` on this column).
  `ProgramsRepo.createProgram()` captures
  `BlueprintAdapter.getManifest().sourceCommit` once, at creation, never
  overwritten afterward. 3 new tests in `tests/programsRepo.test.ts`
  (Phase 1 had no dedicated ProgramsRepo test file at all — this also
  closes that gap).

`CONTRACT_VERSION` bumped `1.0.0` -> `1.1.0` (additive: new fields/tables,
no existing field removed or repurposed).

## Why

Closes 4 of the 6 shortcomings identified in review before the actual
Training Exposure / programming engine work begins — see
`docs/open-decisions.md` and the forthcoming
`docs/TRAINING_EXPOSURE_MODEL.md` for what's still open. No AI/LLM
involved; no volume optimizer, recovery engine, or workout generator was
implemented, per the spec's explicit scope boundary.

## Compatibility note

`programs.blueprint_commit` is `NOT NULL` with no default. Any local dev
SQLite file created before this commit predates that column — `CREATE
TABLE IF NOT EXISTS` does not retroactively add it, so a stale file will
fail on the next `INSERT INTO programs`. Delete the local dev DB file and
let `src/db/client.ts` recreate it; no production data exists yet (see
`docs/deployment.md`), so this is not a migration concern outside of a
developer's own machine.
